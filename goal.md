### Workspace UX architecture

- A pathless authenticated workspace layout owns the host auth guard, admin stylesheet, HeroUI Pro `AppLayout`, sidebar/navbar, responsive aside behavior, logout, and shared pending/error/not-found handling.
- Child pages own only their page header, route-specific actions, data, and content. Do not mount a second `AppLayout` inside a child route.
- Primary workspace navigation is `Campaigns`, `Analytics`, and `Settings`. `Operate` is a contextual campaign-game action, not a global destination with an implicit campaign.
- A campaign context header/navigation exposes `Overview`, `Games`, `Rewards`, `Distribution`, and a campaign-filtered analytics link.
- Active navigation must work for nested paths; breadcrumbs, document titles, and page titles derive from the route/campaign context.
- Campaign and analytics selection must live in dynamic path segments or validated search params, not hidden `useState` defaults.
- Use links for navigation and buttons for actions. Preserve modifier-click, open-in-new-tab, browser history, focus, and scroll behavior.
- Standardize loading, empty, error, forbidden, and not-found states through shared primitives with route-specific copy and recovery actions.
- Unsaved editor state must be explicit. Navigation away from a dirty game/campaign form must either save, discard with confirmation, or remain on the page; silent loss is not acceptable.
- Desktop and mobile actions must have one semantic source. Responsive relocation is allowed, but the same primary action must not appear twice simultaneously.
- Host/admin UI uses HeroUI/HeroUI Pro components and semantic tokens from `docs/admin-design-system.md`.
- Li xi station/public participant UI continues to use `design_system.md` and the template registry. Admin standardization must not flatten or recolor the guest stage.

### Minimum backend/API support

- Add only the owner-authorized queries/mutations required to address campaigns and campaign games by route identity.
- Existing campaigns must resolve or materialize their default li xi `campaignGame` before a canonical game/operator route is generated.
- A route parameter must never be trusted as proof of ownership. Convex helpers verify owner -> campaign -> campaign game relationships.
- The new route model must support multiple campaign-game rows structurally, even though li xi remains the only active template in this task.
- New share links use `/play/$publicCode`; legacy `/claim` links and their 24-character lowercase-hex, expiry, idempotency, capacity, and privacy policies remain unchanged.

### Things that do not change

- TanStack Start, Vite, Nitro, React, Convex, Convex Auth, Google OAuth, HeroUI, R2, Polar, Aggregate, and Sharded Counter remain the chosen stack.
- Current li xi rules, reward allocation, participant uniqueness, station/public session semantics, analytics idempotency, and visual design remain behaviorally compatible.
- Legacy table names can remain behind the li xi boundary; this task does not perform destructive data-model renames.
- `VITE_` remains the only frontend public environment-variable prefix.
